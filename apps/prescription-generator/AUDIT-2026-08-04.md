## 2. Auth

**Confirmed: no login at all. Fully standalone from the staff user system.**

Evidence:
- No `middleware.ts`, no `/api` routes, no auth/JWT/session/cookie usage in this app
- Dependencies: only Next, React, pdf-lib, react-hook-form — no auth SDK
- No env-based auth secrets in-app
- Deploy note (`DEPLOY-AMPLIFY.md`): hosts Next without additional API services

**Not tied to** `hipaa_training_users` / `integrations/hipaa-training-api` / Siya staff portal.

Anyone with the URL can open the form and download PDFs. This matches the earlier “separate/minimal” finding and is currently **more extreme than “minimal auth” — it is zero auth**.

| Mechanism | Present? |

| Database | No |
| localStorage / sessionStorage / IndexedDB | No |
| Server save / API | No |
| Past prescriptions / history | No |
| Saved medication templates | No |

**Flow:** fill form → `generatePDF(...)` → Blob → browser download `prescription-<timestamp>.pdf`. Closing the tab loses the draft (unless the browser restores form state).

## 4. Signature handling

### In this app
- Signature is a **static** file: `public/signature-sneh-pandey.png`, fetched on mount into memory and passed to pdf-lib
- No signature upload UI
- Fallback text if embed fails: `"Sneh Pandey"` (hardcoded in `generatePDF.ts`)
- `LetterheadUpload` shows client-side image→data-URL pattern for logos, but is unwired and does not cover signatures

### Broader monorepo reuse
| Candidate | Finding |
|-----------|---------|
| Staff portal avatar / signature upload | **Not found** |
| `hipaa_training_users` image columns | **None** (id, email, password_hash, name, role, timestamps) |
| Vercel Blob / S3 / Uploadthing / Cloudinary | **Not used** in monorepo package.jsons for this purpose |
| Closest upload middleware | OET LMS `multer` — **audio only**, wrong domain |

**Verdict:** Signature image support for a clinic profile would be **net new** for persistence. The only reusable local pattern is this app’s own client-side `FileReader` / canvas→PNG→pdf-lib bytes path (ephemeral). Any “save signature per login” needs new storage (and likely auth first).

## 6. Multi-tenancy readiness

### What assumes a single clinic today

1. `PRACTICE_INFO` in `generatePDF.ts` — sole clinic text source for PDF  
2. Static JSX header in `page.tsx` — duplicate hardcode  
3. Hardcoded doctor/reg in `PrescriptionPreview.tsx`  
4. Form defaults fixed to Amcare / Dr. SP Pandey  
5. Form→PDF disconnect (clinic fields ignored)  
6. Static `public/` logo + signature assets for every generation  
7. Hardcoded signature fallback name `"Sneh Pandey"`  
8. No user/clinic ID, no profile store, no auth to attach a profile  
9. Unused `DoctorDetails` / `LetterheadUpload` are session-override scaffolding, **not** a clinic-profile system  
10. No server layer to persist or resolve profiles  

### What is already friendly to a profile concept

- Typed fields for doctor/contact/address/reg (add clinic name; wire to PDF)
- pdf-lib already accepts logo/signature bytes
- Dead components roughly sketch “edit clinic details + upload letterhead”
- No DB schema to migrate — greenfield for persistence

### Restructuring needed for “any clinic later”

| Layer | Effort |
|-------|--------|
| Parameterize PDF + UI from a `ClinicProfile` object | Small |
| Persist profile (local vs server) + upload assets | Medium |
| Auth + “one profile per logged-in user” | Medium (integration choice) |
| True multi-clinic per org, admin of many clinics, shared templates | Larger |

## Recommended path

### Near-term (your clinic now — small)

Goal: **one editable clinic profile** (name, address, contact, doctor line/degree/reg, logo, signature) that is **saved and reused** as the letterhead template for every new Rx — without building multi-tenant SaaS.

Suggested shape (decision only — not implementing):

1. **Define a `ClinicProfile` object** (add `clinicName`; keep existing doctor/address/contact/reg; optional logo + signature as data URLs or blob refs).
2. **Wire form → PDF** — delete/replace `PRACTICE_INFO` with profile fields; mount (or replace) `DoctorDetails` + letterhead/signature upload.
3. **Persist lightly first:**
   - **Option A (smallest):** `localStorage` / IndexedDB profile on this device — no auth, still public URL risk.
   - **Option B (better for “per login”):** reuse **staff portal auth** (`hipaa_training_users` + auth API) and store profile JSON (and later blob URLs) server-side keyed by user id — aligns with “saved per login.”
4. Keep prescription content **ephemeral** for now (or add optional “last draft” local only). Medication templates can wait.
5. Signature: client upload → normalize to PNG → store with profile (blob/base64 initially); reuse on every PDF.

This is mostly **wiring existing dead UI + parameterizing one constant**, plus a persistence choice. Layout stays.

### Later (other clinics / true multi-tenant)

Defer until your own clinic profile is solid:

- Org/clinic entities distinct from user (one user → many clinics, or clinic memberships)
- Shared medication formulary / Rx templates per clinic
- Audit log of generated prescriptions (PHI-sensitive — compliance design required)
- Asset hosting (Vercel Blob / S3) instead of huge base64 in DB
- Admin roles, branding themes, multi-prescriber under one clinic
- Do **not** invent a second auth island — attach to staff auth when you cross this line

### Explicit non-goals for near-term

- No full multi-clinic admin console  
- No prescription history vault with PHI unless compliance path is designed  
- No net-new surveillance or ERP around this tool  
- Do not keep Amcare hardcodes once profile is wired (single source of truth)

---

## Bottom line

The app is a **thin, unauthenticated, single-clinic PDF printer** with a partially designed (but unwired) clinic-details layer. pdf-lib **can** support variable letterhead; clinic text is the main hardcoded blocker. Auth is **absent**, not “minimal staff auth.” Signatures are a static PNG; persisted uploads would be net new. The smallest valuable next step is a **ClinicProfile + wire-to-PDF + save-per-user (or local)**, not multi-tenant restructuring.
